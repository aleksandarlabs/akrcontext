# TASK-009

## Goal

Make every akrctx agent configurable from `.akrctx/config.json`: which agents exist, when
they trigger, which hosts they are emitted for, and which model each host should run them
with.

Today an agent is configurable in name only. `judge.enabled` and
`comprehensionGate.enabled` are booleans, the trigger is a single-value literal that cannot
hold another value, the per-host agent files are frozen `Record<string, string>` constants,
and the judge template ends by telling the reader to hand-edit the generated frontmatter to
choose a model — a change the next `akrctx upgrade` overwrites. So the one setting a
developer most wants to control is the one setting the harness cannot persist.

This task introduces the `agents` block as the canonical shape for all three akrctx agents,
maps the existing keys onto it without breaking any configuration in the wild, and makes
the generated agent files a function of that configuration rather than a constant.

## Recommended Workflow

SDD+TDD

## Workflow Notes

- Workflow source: `.akrctx/config.json` `workflowRules.apiOrContract` is `SDD+TDD`.
- Why this workflow: this is a schema contract with two readers that cannot be changed
  together — configurations already on disk in other repositories, and the generated agent
  files three different hosts parse. The normalization rules and the precedence rule have
  to be settled as a specification first, then pinned by failing tests, because a
  regression here is silent: a config that stops being honoured looks exactly like a config
  that was never set.
- Research-first discovery was completed before this capsule: `normalizeConfig` already
  normalizes `comprehensionGate` but spreads `judge` through untouched; `desiredManagedFiles`
  in `src/upgrade.ts` selects agent files by `config.judge?.enabled` and
  `config.comprehensionGate.enabled`; `getJudgeGap` hardcodes the three judge paths;
  `judgeAgents` and `comprehensionAgents` are static per-target constants; and `pi` is
  excluded from both agent maps by type (`Exclude<Target, "pi">`).

## Contract

### The `agents` block

- `agents` is the canonical configuration for akrctx agents. It holds exactly three
  entries — `judge`, `comprehension`, `implementer` — and no others. A project cannot
  declare an agent of its own here.
- The three are fixed because each one's trustworthiness comes from a CLI contract, not
  from its prose: `judge verify --run-tests`, the comprehension gate schemas, and the
  `akrctx impl` attempt store. An entry with no command behind it would be an agent akrctx
  generates and cannot vouch for, which is the failure mode the harness exists to remove.
- Each entry accepts: `enabled` (boolean), `trigger` (string), `targets` (subset of the
  installed targets), and `model` (a per-target map). `agents.implementer` additionally
  accepts `maxAttempts`.
- Every field is optional. An absent field falls back to the built-in default for that
  agent, which is the behaviour that ships today.

### Compatibility with `judge` and `comprehensionGate`

- Existing configurations keep working untouched. `normalizeConfig` reads legacy `judge`
  and `comprehensionGate` and maps them onto the `agents` shape in memory, exactly as it
  already normalizes `comprehensionGate` today.
- Reading a legacy config never rewrites it. `akrctx upgrade` does not migrate the file,
  and no command edits a key the user did not ask to change. A developer who never opens
  the new block never sees it appear in their diff.
- `agents` is the canonical form on write. When a command changes an agent setting, it
  writes to `agents.<name>`. Legacy keys are left as they are rather than deleted, so a
  downgrade to an older akrctx keeps reading a valid file.
- When both forms are present and disagree, `agents` wins and Doctor reports the
  divergence, naming both paths and the value in effect. Silently honouring one of two
  contradictory settings is the failure this whole task is about; the resolution has to be
  visible.
- `judge.enabled` and `comprehensionGate.enabled` remain readable and writable for as long
  as they exist. Nothing in this task removes, renames, or adds to them.
- `impl.enabled`, the optional key TASK-008 introduces, maps onto `agents.implementer` by
  the same rule.

### Models

- `model` is per target, because the identifier space is per host: `{ "claude": "...",
  "codex": "...", "copilot": "..." }`. There is no single value that means the same thing
  in all three.
- A configured model is written into the generated file at the place that host reads it —
  the `model` frontmatter field for Claude and Copilot, the `model` key for Codex TOML —
  and the file is regenerated by `akrctx upgrade` from the config, so the setting survives
  regeneration. This replaces the closing paragraph of the current judge template, which
  tells the reader to hand-edit a generated file.
- Validation is by pattern per target, not by a list of identifiers. A list of model names
  goes stale on every provider release and would make a new model unusable until akrctx
  ships a version that knows about it; a pattern does not expire.
- A model that does not match its target's pattern is a warning, never an error. The value
  is written literally to the generated file anyway. akrctx does not know the provider's
  catalogue, so refusing an unrecognised identifier would block a legitimate new model to
  catch a typo — the wrong trade in both directions.
- The warning says what was configured, which target it applies to, and what that target's
  identifiers usually look like. It appears in the output of `enable`, in `doctor`, and in
  `upgrade`, and the generated file itself carries a comment naming the config path that
  controls its model.
- An absent `model` for a target keeps today's behaviour exactly: the field is omitted and
  the host picks its own default.

### Triggers

- `trigger` is a free string. Known values for an agent are propagated to the generated
  instructions and to `status`; an unknown value is propagated too, with a warning that
  names the values akrctx recognises.
- This follows the same reasoning as models. akrctx cannot enumerate every point in a
  workflow a project might want an agent invoked at, and rejecting an unknown trigger stops
  work to prevent a typo.
- The trigger is declarative. akrctx validates and propagates it; it does not enforce it.
  No command rejects a record because of when it claims to have run, and the generated
  instructions do not imply otherwise. The lead agent decides when to invoke.

### Targets per agent

- `targets` restricts an agent to a subset of the installed targets. Absent means every
  installed target that has a format for that agent, which is today's behaviour.
- A target listed for an agent but not installed is a warning and is skipped, not an error.
  The same for a target with no format for that agent.
- Only the installed targets are ever written to. `agents.<name>.targets` narrows the set;
  it never widens it beyond `config.targets`.

### Pi

- Pi is a supported akrctx target but has no agent format. `judgeAgents` and
  `comprehensionAgents` exclude it at the type level, and this task does not add it.
- Configuring `pi` under any agent's `targets` produces the same warning as any other
  target without a format, and Doctor states the limitation rather than staying silent
  about a target the user explicitly asked for.
- The gap is recorded as debt in `.akrctx/wiki/decisions.md`, with what would be needed to
  close it. Claude Code, Codex, and Copilot are the three supported hosts.

### Attempt budget

- `agents.implementer.maxAttempts` is defined, validated, and defaulted to 3 by this task.
- This task does not implement the implementer agent, `akrctx impl`, or the attempt store.
  It defines the schema so that TASK-008 consumes an existing key instead of moving the
  schema again.
- A value that is not a positive integer is rejected. This one is an error, not a warning,
  because unlike a model identifier akrctx fully knows the valid domain, and an
  unparseable budget would otherwise resolve to "no limit" — the exact failure TASK-008
  exists to prevent.

### Command surface

- `akrctx config set` accepts the `agents.<name>.<field>` keys, alongside the keys it
  accepts today.
- `akrctx judge enable` and `akrctx comprehension enable` keep working with their current
  arguments and write to `agents` instead of the legacy keys. Their output gains the model
  and target report described above.
- No command is renamed or removed.


## Out Of Scope

- Implementing the implementer agent, `akrctx impl`, or the attempt store. TASK-008 owns
  those and is rewritten against this schema afterwards.
- A Pi agent format.
- User-declared agents beyond the three built-in ones.
- Enforcing triggers, permissions, or tool lists at runtime. akrctx generates definitions;
  a host's permission rules are session-scoped and akrctx cannot impose them.
- Migrating configurations on disk, or deleting legacy keys.
- Per-agent prompt or instruction overrides.

## Clarifications

### Session 2026-08-06

- Q: Does the `agents` block cover only akrctx's three agents, or can a project declare its
  own? / A: Only the three built-in ones. Each has a CLI contract behind it; an entry with
  no command behind it would be an agent akrctx emits and cannot vouch for.
- Q: What is the relationship between `agents` and the existing `judge` and
  `comprehensionGate` keys? / A: `agents` is canonical and the legacy keys map onto it.
  Old configurations keep working and are not rewritten; the legacy keys are deprecated,
  not removed.
- Q: Are model identifiers validated against a known list, or passed through? / A:
  Validated — but by pattern per target rather than by a list, because a list goes stale on
  every provider release and would block a new model until akrctx shipped a version that
  knew it.
- Q: What happens when a configured model does not match its target's pattern? / A: The
  value is written to the generated file literally and akrctx warns. Never an error, and
  never silently dropped: blocking on a typo heuristic would stop legitimate work, and
  omitting the field would run the agent on a different model than the one requested.
- Q: Where does the warning, and the statement of where a model is configured, appear? /
  A: In `enable`, in `doctor`, in `upgrade`, and as a comment inside the generated agent
  file itself.
- Q: Are triggers validated against an enum, enforced by the CLI, or free text? / A: Free
  text with a warning for unrecognised values, propagated to the generated instructions.
  Declarative only; no command enforces a trigger.
- Q: Which fields are configurable per agent in this task? / A: `enabled`, `trigger`,
  `model` per target, `targets`, and the implementer's attempt budget.

## Open Questions

- When `agents` and a legacy key disagree, this contract resolves to `agents` and reports
  the divergence in Doctor. Whether `enable` should additionally refuse to write while a
  contradictory legacy key is present, rather than adding a second source of truth to an
  already-divergent file, is undecided.
- Whether a model warning should also be emitted by `akrctx status`, which today reports
  agent state but is not listed among the surfaces above, was not asked and is not assumed.
