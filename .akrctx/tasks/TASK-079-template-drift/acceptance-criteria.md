# Acceptance Criteria

Every criterion is one top-level `- ` bullet that starts with `AC-<n>: `. The judge reports a
typed result per identifier, so identifiers must be unique and must never be reused for a
different criterion. Indented lines continue the bullet above them.

- AC-1: An installed capsule template that matches its recorded hash is updated when the source
  template changes, and `upgrade` lists the write.
- AC-2: An installed capsule template a project has edited is never overwritten. The project is
  offered the new content through the existing suggested-file path.
- AC-3: A fresh install and an upgrade eligible for automatic update produce identical
  capsule templates. Personalized or unprovenanced differing files retain their contents until
  a candidate is explicitly accepted.
- AC-4: Project wiki knowledge keeps its current preserve behaviour. No test that protects it
  changes.
- AC-5: `upgrade --dry-run` names differing capsule template paths and their planned
  update or candidate action; it changes neither files nor the provenance manifest.
- AC-6: No capsule template is regenerated by hand anywhere in the delivery.
- AC-7: The claim in capsule context about regenerated harness files is true after this change,
  or the claim is corrected.
- AC-8: Existing agent instruction files are preserved unless a human approves a merge.
- AC-9: The review checklist is completed before handoff.
- AC-10: A differing existing capsule template without a matching hash is preserved and gets
  an upgrade candidate, including missing/invalid-manifest cases. No historical hash is invented.
- AC-11: Fresh installs record hashes for all capsuleFiles templates. Already-identical
  templates can acquire provenance without rewriting their content.
