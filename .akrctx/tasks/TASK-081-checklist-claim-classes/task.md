# TASK-081 — Separate evidence references from process attestations

## Goal

Simplify the shipped checklist and distinguish evidence references from process attestations.
Mechanically verified outcomes point to acceptance criteria or existing validation evidence;
the checklist does not duplicate their verification. Process attestations name the asserting
actor and are explicitly self-reported, including when that actor is the implementing agent.

## Problem evidence
The checklist is written, ticked and used by the same actor. In TASK-075 the implementing agent
ticked twelve boxes, including "Red tests written before implementation". The implementation
log reports that sequence, but the completed code and checkbox do not establish it independently.
The judge must not receive the implementing agent's narrative as evidence, so the assertion needs
to be labelled as self-reported rather than independently verified.

Other items in the same checklist are mechanically decidable and are checked by hand anyway:
"`JUDGE_SCHEMA_VERSION` is 6", "Build, full tests, lint and required CLI checks run", and
"Shipped harness files regenerated from src/templates, not hand-edited". The last one was false
in spirit during TASK-075, because the capsule template had to be regenerated by hand, and the
box was ticked.

policy.json sets `requireReviewChecklist: true`, so the file is mandatory. Nothing checks its
content, so the requirement buys a file and not a fact.

## Contract

- This first delivery changes checklist guidance and generated templates, not verify behavior.
  No checklist parser, notices channel or new record field is introduced.
- Use two plain Markdown sections: Evidence References and Process Attestations. Evidence
  references point to existing AC identifiers or declared validation commands; references are
  locators, not a new proof mechanism or a second set of pass/fail claims.
- Attestations identify the asserting role, such as implementing agent or human operator.
  A checked box does not authenticate the author or make an assertion independently verified.
- Remove duplicated mechanical-result checkboxes from the shipped template. Retain useful
  process assertions that cannot be independently reconstructed from final code.
- Preserve TASK-051: complete the checklist before snapshot capture; the verified judge
  record, not a post-approval checkbox, establishes completion of independent review.
- Existing capsules remain valid and are not migrated. Future generated checklists use the
  simpler layout; no new gate changes `valid` or `approved`.

AC-2 and AC-3 are retired because verify notices are outside this delivery. Their identifiers
are not reused; AC-10 and AC-11 cover template assertions and removal of duplicated claims.

## Out Of Scope

- A checklist parser, machine verifier, verify notices, new record field or approval gate.
- Authenticating who checked a box or treating self-attestation as human approval.
- Re-running checks already represented by validation evidence or AC results.
- Migrating existing capsules or reversing TASK-051's pre-snapshot checklist rule.
